# 智能空间（元社交）二期后端功能需求评估

> 目的：基于当前前端 Demo 的页面完成度，**全面盘点二期后端需要实现的功能**，用于评估后端实际开发难度与工作量。
>
> 结论先行：当前 `www/` 是纯静态 HTML 原型（无任何真实后端），29 个页面全部硬编码数据、交互均为前端本地模拟。二期要让 Demo 跑成可用产品，后端覆盖的**业务模块多达 10 大类、预计 200+ 个 API 端点**，属于一个**中等偏大的社交 + 商城 + 虚拟空间产品后端**，绝非"简单 CRUD"。
>
> 日期：2026-08-03

---

## 五、技术难点与风险（按影响排）

1. **IM 实时性**：WebSocket 长连接、消息顺序、已读回执、离线补拉、多端同步 —— 建议选成熟云服务或严格限定 MVP 范围（仅文本）。
2. **手机号一键登录**：依赖运营商（天翼/移动/联通）网关 SDK 与商务接入，**涉及资质/合同，通常是项目阻塞项**。
3. **支付与虚拟币**：微信/支付宝支付需商户号资质；「星币」需余额/流水体系，合规需谨慎。
4. **推送**：Android 厂商通道（华为/小米/OPPO/vivo）逐个适配，工作量不小；Demo 阶段可降级为轮询。
5. **LBS**：定位上报 + 附近查询（Redis GEO / MySQL 距离计算），并发与冷启动定位精度。
6. **内容安全**：UGC 文本/图片审核，正式商用必备，选云审核 API 即可。
7. **数据合规**：实名制（虚拟身份证含姓名/出生）、隐私条款、个人信息保护 —— 涉及合规评审。
8. **3D 房间**：Godot 方案尚未确认；一旦做真 3D，后端要下发房间配置、热点、3D 资源 CDN，接口模型需预留。

## 六、工作量与难度评估

> 以"1 人日 = 1 个熟练后端工程师一天"粗略估算，不包含联调与返工。

| 方案 | 内容 | 预估人日 | 难度 |
|---|---|---|---|
| **A. MVP（Demo 可跑）** | 认证登录（短信+一键登录降级为模拟）、用户资料、好友、基础 IM（长连接轮询）、帖子、房间、商品+购物车（无支付）、公告 | 45~60 | ★★★☆ |
| **B. 完整版（A + 全量）** | A + 真实 IM 服务、支付、推送、商家后台、内容审核、运营后台、监控 | 120~180 | ★★★★ |
| **C. 选云服务简化** | 用腾讯云/阿里云：IM、推送、短信、对象存储、内容审核全套托管 | 可把 B 压缩到 **60~80** 且稳定性更好 | ★★★ |

### 关键判断

- **纯自研 + 完整版**：约 **4~6 人 × 3 个月**，属中型社交产品后端，难度在 IM 与支付。
- **云服务组合 + MVP**：约 **2 人 × 1~1.5 个月** 即可支撑一期客户演示，最划算。
- **不建议**：用单机 Python/Node 直连做 IM 和支付，稳定性与合规都过不了关。

## 八、前端改造的连带影响（提醒）

后端不是全部工作，前端也要从"硬编码"改为"接接口"：

1. 29 个页面需要引入请求层（fetch/axios）、Token 注入、错误处理、Loading 态。
2. `index.html` 5 Tab iframe 架构 + 登录态需跨 iframe 共享（localStorage/sessionStorage 同源问题）。
3. 所有模拟数据（`allPosts`、`friendsData`、`products` 等）需迁移为接口返回 + 分页。
4. 外链图片需迁移到自有 CDN / OSS，避免失效。
5. `panorama_room.html` 若接 Godot 3D，前端嵌入方式会变，需预留接口契约。
